## 🔴 1. サーバーにパスワードで root ログインできる

**今の状態**
- 本番サーバー（Xサーバー VPS）のSSH（＝サーバーに遠隔で入る入口）が、
  - `PermitRootLogin yes`（最高権限の root で直接入れる）
  - `PasswordAuthentication yes`（**鍵がなくてもパスワードで入れる**）
- root にはパスワードが設定されている（2026-06-25 設定）。
- 直近24時間で **約19,000回** のログイン失敗記録。世界中の自動プログラムが総当たりで root のパスワードを当てようとしている。
- 回数制限の仕組み（fail2ban など）は入っていない。
- 実際に成功したログインは、Mac の鍵によるものだけ（＝今のところ侵入の形跡はなし）。

**なぜ危ないか**
- root のパスワードが当てられた瞬間、サーバーのすべて（記事DB・書き手のメールアドレス・バックアップの鍵・メール送信の鍵）を握られる。
- パスワードの強さ次第だが、「入口が開いていて毎日叩かれている」こと自体が一番大きなリスク。

**対策（おすすめ順）**
1. SSHを「**鍵のみ**」にする：`PasswordAuthentication no`、`PermitRootLogin prohibit-password`。
   - ⚠ やる前に、Macの鍵で入れることを必ず確認（入れなくなると締め出される）。Xサーバーの管理画面の「コンソール」が非常口になる。
2. 余裕があれば fail2ban（失敗を繰り返す相手を自動で締め出す仕組み）を入れる。

**✅ 対応結果（2026-10-22）**
- `/etc/ssh/sshd_config.d/00-key-only.conf` を追加（`PasswordAuthentication no`・`KbdInteractiveAuthentication no`・`PermitRootLogin prohibit-password`）。元の設定ファイルは書き換えず、控えを `/etc/ssh/sshd_config.bak-20261022` に保存。
- 反映後に確認：Macの鍵で入れる・サイトは正常に動いている・鍵なしの相手には「publickey（鍵）のみ受け付け」と返して断る。
- 元に戻すとき：上の追加ファイルを消して `systemctl reload ssh`。

## 🔴 2. 部品（ライブラリ）の既知の弱点

`npm audit`（部品の弱点を調べる公式の道具）の結果：**37件（重大1・高7・中29）**。

主なもの：

| 部品 | 何に使っているか | 弱点の中身 | 実際の危なさ |
|---|---|---|---|
| next（16.2.6） | サイト本体 | 重大3件・高5件など計17件 | 中〜高：※下の補足 |
| sanitize-html（2.17.4） | 本文の危ないタグを取り除く係 | 一部の書き方で、取り除きをすり抜けられる | 中：書き手のアカウントが乗っ取られたとき、読者のブラウザで悪さをされうる |
| prosemirror-view | 投稿画面のエディタ | 貼り付け時にスクリプトが動きうる | 中：書き手が悪意あるページからコピーして貼ると危ない |
| sharp（0.34.5） | 写真の縮小 | 画像処理部品の弱点 | 中：細工した画像でサーバーを止められる等。ログインした人しか上げられないので限定的 |
| nodemailer（8.0.10） | メール送信 | 細工した宛先でサーバーを止められる | 低：宛先はこちらで決めているので通常は届かない |
| postcss / source-map-js | 見た目の組み立て（作る時だけ） | — | 低：公開中のサイトでは使われない |

**next の補足（このサイトに当てはまるか確認済み）**
- 重大3件（外からサーバーを操れる種類）は、①画像最適化の機能（このサイトは使っておらず、本番で `/_next/image` が404になることを確認）、②OG画像を自動で作る機能（使っていない）、③Windowsサーバー（Ubuntuなので無関係）が対象。**今のところ直接は当てはまらない**。
- ただし「サーバーを重くして止める（DoS）」「キャッシュの取り違え」など、当てはまりうるものが残っている。将来その機能を使い始めたときに危険になるので、**16系の最新版へ上げておくべき**。

**対策**
- `npm audit fix`（互換性を保つ範囲の更新）で直るもの：sanitize-html・prosemirror-view・source-map-js。
- 大きめの更新（動作確認が必要）：next → 16.4系、sharp → 0.35系、nodemailer → 10系。
- 手元で更新 → 動作確認（投稿・画像・動画・ログイン）→ 本番反映、の順で進めるのが安全。

## 🟡 3. 公開サイトに「守りのヘッダー」がない

ヘッダー＝サーバーがページと一緒にブラウザへ送る「取り扱い注意書き」。今は何も付いていない。

| 足すもの | 効果 |
|---|---|
| `X-Frame-Options: SAMEORIGIN`（または CSP の frame-ancestors） | 他人のサイトに投稿画面を透明に埋め込んで、気づかないうちにボタンを押させる攻撃（クリックジャッキング）を防ぐ |
| `X-Content-Type-Options: nosniff` | アップロードされたファイルを、ブラウザが勝手に別の種類（HTMLなど）として扱うのを防ぐ |
| `Strict-Transport-Security` | 一度来た人は必ず暗号化通信（https）でつながるようにする |
| `Referrer-Policy: strict-origin-when-cross-origin` | 外部リンクを踏んだとき、こちらのURLの細部を相手に渡しすぎない |

あわせて、サーバーの種類・版（`nginx/1.28.3 (Ubuntu)`・`X-Powered-By: Next.js`）を名乗らないようにするとよい（攻撃者に手がかりを与えない）。

**対策**：Nginx の設定に数行足す＋`next.config.ts` に `poweredByHeader: false`。

## 🟡 4. サイトが root 権限で動いている

- PM2・サイト本体（next-server）がともに root で動いている。
- もし部品の弱点（上の2）を突かれてサイトが乗っ取られると、そのままサーバー全体が乗っ取られる。
- 専用ユーザー（例：`app`）で動かせば、被害をサイトのフォルダ内に閉じ込められる。
- `docs/deploy-notes.md` §8 の「本番化TODO」に残っている項目。

**対策**：専用ユーザーを作り、フォルダの持ち主を変えて、PM2 をそのユーザーで起動し直す（作業中は数分サイトが止まる）。

> 補足：サーバー内のファイアウォール（ufw）は止まっているが、Xサーバーの管理画面のパケットフィルターが効いており、**外から届くのは 22・80・443 だけ**だった（ポート3000には外から届かないことを確認済み）。現状これで問題なし。

## 🟢 5. 招待を受けていない人の「仮パスワード」が推測できる形

- 書き手を登録したとき、仮のパスワードを `invite-pending-<登録した瞬間の時刻>` にしている（`src/app/actions/users.ts` 69行目）。
- 現在、招待をまだ受けていない人が **4人**。
- 時刻が分かれば候補を絞れる理屈だが、ログインの回数制限（10分に10回）があるので、実際に当てるのはほぼ不可能。
- ただ、ランダムな文字列にしておくのが筋（数行の修正）。

## 🟢 6. その他の小さな改善候補

- **パスワードを変えても他の端末のログインは最大7日残る**：スマホを落とした等で「全部ログアウトさせたい」ときに手段がない。今は書き手を一度削除するしかない。
- **プロフィールのURL欄の中身を確認していない**：`https://` で始まるかを確かめていない。React（画面部品）が危ない `javascript:` を止めるので実害は小さいが、保存時に弾くのが確実。
- **GIF と MP4 は中身を確認せず保存している**：名札（種類）だけで判断。ログインした書き手しか上げられないので危険は小さい。上の「nosniff」ヘッダーを足せば実質的に安全。
- **プレビュー画面は、ログインしていれば他人の下書きも見られる**：記事番号を打ち替えると見える。書き手どうしなので実害は小さい。
- **自動保存では連載の担当チェックをしていない**：下書きを担当外の連載に入れられるが、公開時（「投稿する」）には正しくチェックされる。

## 📋 追加点検（2026-10-28）：門（ファイアウォール）と OS の自動更新

本番サーバーの設定を**読むだけ**で確認し、Mac から外向きにノックして実際に入れる入口を確かめた（何も変更していない）。

**門（ファイアウォール）＝✅ 合格**
- サーバーの中の門番（ufw）は**止まっている**（iptables・nftables も空＝何でも通す）。
- 代わりに **XServer 管理画面の「パケットフィルター」が効いている**。外から開いているのは 22（SSH・鍵のみ）／80・443（Web）の3つだけ。3000・3306・8080 などは閉じている。
- ⚠ サイト本体（Next.js）の **3000番はサーバーの中では「どこからでも受け付ける」設定**（`*:3000`）。今は外側の門番が止めているが、**パケットフィルターを無効にすると外から裏口が見える**。→ **パケットフィルターは「オン」のまま触らない**。
- 将来の二重の守り（🟢低）：Next.js を `127.0.0.1`（＝サーバー自身からだけ）で待ち受けるようにする。Nginx は中から呼ぶので、サイトの見え方は変わらない。
- fail2ban は入っていない。SSH が鍵のみなので現状は不要（あれば安心、程度）。

**OS の自動更新＝✅ 合格**
- `unattended-upgrades` が有効で毎日動いている（対象＝Ubuntu の安全のための更新）。例：10/28 06:22 に nginx・libbrotli1 を自動更新。
- 「再起動が必要」の札は出ていない（稼働10日）。
- 安全のため以外のふつうの更新が65個たまっている（自動では入らない設定。たまに手作業でまとめて入れれば十分）。

## ✅ 良かった点（守れていたところ）

- パスワードは scrypt（元に戻せない方式）で保存。生パスワードは保存していない。
- ログイン・パスワード再設定・お便りフォームに**回数制限**あり。回数の数え方（どの回線か）もNginxが正しく渡しており、偽装できない。
- 招待・再設定のリンクは使い捨て・期限付き・DBには指紋だけ保存。メールのリンク先は固定のサイトURL（すり替え不可）。
- 会員証（Cookie）は https のときだけ送られ、JavaScriptから読めない設定。本番の秘密鍵は手元のものとは別に作り直されていた。
- 本文は保存時と表示時の2回、危ないタグを取り除いている（許可したものだけ残す方式）。
- 記事の編集・削除は「本人か管理者か」をサーバー側で確認している。管理者専用の操作もすべてサーバー側で確認。
- DBへの問い合わせは安全な書き方（SQLインジェクション対策済み）。
- `.git`・`.env.local`・DBファイルは外から取れないことを確認（すべて404）。
- https の証明書は自動更新が動いている（30nen.com は 12/26 まで有効）。
- OSの自動セキュリティ更新は有効。
- 秘密設定ファイル・バックアップの鍵ファイルは持ち主だけが読める設定。
