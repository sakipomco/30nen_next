## 1. このサイトは何か

- **20名以上の書き手が毎日投稿する公開日記サイト**。2024年開店、記事は約8,600件。
- 書き手はITに詳しくない方が多く、スマホから投稿します。スペイン語話者が2名います。
- 読み手は日々の日記を読みに来ます。検索やアーカイブから過去記事も遡ります。

### なぜ引っ越したか

- WordPress の管理・保守の手間を減らす
- 書き手が迷わない**シンプルな投稿画面**にする
- 月額のSaaS費用をゼロにする（サーバー代のみ）
- 既存記事を**全件**持っていく

### なぜ SQLite か

同時書き込みが軽い（各人が1日数回「投稿」を押す程度）ため、SQLite で十分と判断しました。将来 数百人規模の高頻度同時書き込みになれば MySQL/PostgreSQL への移行を検討します。そのための保険として、記事テーブルに旧WordPressのID（`articles.wp_id`）を保持しています。

---

## 3. 移行で何をしたか

1. WordPress の MySQL から全記事を JSON で書き出し（`migration/export/all-posts.json`・36MB）
2. 本文HTMLを整形（`migration/lib/transform.ts`）
   - `wpautop` 相当：WPは本文を「素のテキスト＋空行」で保存しているので、空行→`<p>`、単一改行→`<br>` に変換
   - 画像URLを絶対URL（`https://30nen.com/wp-content/uploads/…`）から相対パス（`/uploads/…`）へ書き換え
   - 無害化（投稿時と同じ許可リストを通す）
   - 日時を日本時間 → UTC へ変換
3. 画像を運搬（71GB → 約6.4GB に縮小）。HEIC は JPEG へ変換
4. 旧URLからの転送を用意（後述）
5. ドメインを新サイトへ向けて切替

## 4. いま特に見ていただきたいところ

正直に申し上げると、**切替後の2日間で、移行時に静かに失われていたものが4つ見つかりました**。どれも「動かない」のではなく「気づかないと分からない」種類の欠落でした。同じ性質の見落としがまだあるかもしれない、というのが今いちばんの不安です。

### 4-1. 見つかった欠落（すべて7月31日に修正済み）

| 何が消えていたか | 原因 | 規模 |
|---|---|---|
| Spotifyのプレイヤー | WPの oEmbed（URLを1行書くと自動で埋め込みになる）を使っていた。移行後はただの文字列として残った | 16記事・18か所 |
| グレー文字 | WPは `<span style="color:#999999">` と直接書いていた。無害化が `style` を許さないので色だけ落ちた | 181記事・356か所 |
| 長い罫線 | `wpautop` の「中身が空の段落は捨てる」判定が `<hr />` **だけの行を捨てていた** | 193記事中187本 |
| 写真が小さい | WPは本文に縮小コピー（横300pxなど）を貼り、旧サイトのCSSが幅いっぱいに引き伸ばして表示していた。新サイトは実寸表示なので小さく見えた | 3,175枚 |

**共通する原因**は、「旧サイトの見た目は、HTMLだけでなく WordPress の暗黙の挙動（oEmbed・自動整形）と旧テーマのCSSに支えられていた」という点です。HTMLを機械的に移すだけでは再現されません。

**お願い**：同じ種類の見落としが他にないか、`migration/lib/transform.ts` と `src/lib/sanitize.ts` を突き合わせて見ていただけると助かります。特に、旧データにあって新システムの許可リストに無いタグ・属性・記法。既知の残りは SoundCloud（3か所）・Vimeo（2か所）・Voicy（1か所）の埋め込みです。

### 4-2. 無害化（サニタイズ）の設計 — `src/lib/sanitize.ts`

公開ページは `dangerouslySetInnerHTML` で本文HTMLを表示します。投稿画面の制限は飾りで、Server Action には細工したHTMLを直接送れるため、**保存時と表示時の両方**でここを通しています。

許可リスト方式です。今日、次の2つを**意図的に広げました**。ここは特に厳しく見てください。

**① iframe に Spotify を追加**
```
allowedIframeHostnames: ['www.youtube.com', 'youtube.com', 'www.youtube-nocookie.com', 'open.spotify.com']
```
ホスト名だけでは Spotify の通常ページも埋め込めてしまうため、`exclusiveFilter` で **`https://open.spotify.com/embed/` で始まるものだけ**に絞りました。テストで確認した挙動：

- `https://open.spotify.com/embed/track/…` → 通る
- `https://open.spotify.com/track/…`（通常ページ） → 消える
- `https://open.spotify.com.evil.example/embed/…`（偽ホスト） → 消える
- `http://open.spotify.com/embed/…`（暗号化なし） → 消える

**② span に class="gray" だけ許可**
```
allowedTags: [... 'span'],
allowedAttributes: { span: ['class'] },
allowedClasses: { span: ['gray'] },
```
`style` は許していません（好きな見た目を差し込めると危ないため）。色の値はCSS側に持たせています。

**懸念点として自覚していること**：iframe を1つでも許すと、埋め込まれたページが利用者の画面の一部を占めます。同一生成元ポリシーによりこちらのDOMやCookieには触れませんが、`sandbox` 属性は付けていません（Spotify・YouTubeのプレイヤーが動かなくなるため）。この判断が妥当か、意見をいただきたいです。

### 4-3. 認証まわり

- パスワード：`crypto.scrypt`（OWASP推奨方式）。生パスワードは保存しない
- セッション：JWT（`jose`）を Cookie に。有効期限7日（Cookieの `maxAge` とJWTの期限を揃えてある）。秘密鍵は環境変数 `SESSION_SECRET`
- Cookie の属性：`httpOnly: true` / `sameSite: 'lax'` / `secure` は本番で `true`
  - ただし `SESSION_COOKIE_SECURE=false` で一時的に無効化できる抜け道があります（HTTPS未設定のお試しサーバー用に入れたもの）。**本番の `.env.local` にこの変数が無いことを確認済み**＝既定の `true` が効いています。とはいえ、こういう「一時的な逃げ道」がコードに残っていること自体をどう考えるか、意見をいただきたいです
- 権限は2種類（`admin` / `author`）
- 管理ページと Server Action の先頭で `requireUser()` を呼ぶ
- パスワードは書き手本人が設定・再発行する運用（店主は預からない）

**見ていただきたい**：トークン失効の扱い（現状、パスワード変更やログアウトで既発行のJWTを無効化する仕組みはありません。Cookieを消すだけです）、権限チェックの漏れ、招待・パスワード再設定トークンの扱い。`src/auth/` 一式と `src/app/actions/` です。

### 4-4. 旧URLからの転送

- 記事：`/連載名/YYYY/MM/DD/記事ID/` → `/posts/{id}`（`src/app/[category]/[year]/[month]/[day]/[id]/route.ts`）
- 連載トップ：`/連載名/` → `/series/連載名`（`src/app/[category]/page.tsx`・今日追加）

後者はルート直下の1セグメント動的ルートです。Next.js は静的ルートと `public/` のファイルを動的ルートより優先するため `/about` などとはぶつからない、という理解で作りました。本番で全22連載＋主要ページを検査して問題は出ていませんが、**この理解が正しいか**確認していただけると安心です。

### 4-5. 過去に直した、他人の目で見つかった不具合

参考までに。いずれも「動いているように見えて間違っていた」類です。

- **数字だけのslugがidと衝突**：URLを「名前→番号」の順で照合していたため、旧WPから引き継いだ「名前が数字だけ」の記事231件のうち46件が別記事を開いていた。前後の日記・関連記事など番号URLで作るリンクすべてが影響。→ 数字だけのURLは先に番号で探すよう修正
- **親連載の担当だと子連載に書けない**：担当連載しか選択肢に出しておらず、親カテゴリだけ担当する書き手がどこにも投稿できない状態だった。→ 担当＋その子孫を選択肢に含めるよう修正

```

│   ├── (public)/          公開ページ（トップ・記事・連載・検索・アーカイブ）
│   ├── admin/             投稿画面・連載管理・投稿者管理・サイト設定

│   └── [category]/        旧URLからの転送
├── auth/                  パスワード・JWT・セッション
├── db/                    Drizzle スキーマとデータアクセス層
├── lib/                   無害化・画像・メール・日時など
└── components/public/     公開ページの部品

migration/                 移行スクリプトと手順書
scripts/                   運用スクリプト（デプロイ・復元・ユーザー作成）
docs/schema.md             DB設計
HANDOFF.md                 全経緯の記録（これがいちばん詳しい）
```

読む順番のおすすめ：`HANDOFF.md` の §0〜§1 → `docs/schema.md` → `src/lib/sanitize.ts` → `migration/lib/transform.ts`
