# レビュー指摘 2026-07-31（第5回）

レビュー担当: Codex
対象: 2026-07-31 時点のワークツリー（30nen.com 移行後レビュー。主にスパム対策・検索/読みやすさ・セキュリティ全般）

## R-01 〔重要度: 高〕 公開フォームに送信回数制限がなく、スパム送信・メール大量送信に弱い
- 該当: src/app/actions/contact.ts:24
- 指摘: お便りフォームはハニーポットで簡易対策されていますが、IP・メールアドレス・宛先・時間帯ごとの送信回数制限が見当たりません。Server Action は直接POSTできる前提で書かれているため、フォーム画面を経由せず連続送信されると、店主・書き手・SMTPサーバーに大量メールが届く可能性があります。
- 提案: まずは軽量な rate limit を入れるのがよいです。例: IP単位で「1分3通・1日30通」、同一メールアドレス単位で「1時間5通」、失敗/ハニーポット検知時は少し厳しめにする。SQLite に `contact_attempts` のような短期ログを持つか、Nginx 側の `limit_req` を併用すると運用しやすいです。あわせて本文・名前・件名に長さ上限を入れてください。
- 根拠: 現状の検査はハニーポット、必須入力、メール形式、宛先ID確認までで、送信頻度を止める処理がありません（src/app/actions/contact.ts:28-99）。ハニーポットは有効ですが、人間に近いbotや専用POSTには突破されます。

## R-02 〔重要度: 高〕 ログインとパスワードリセットに試行回数制限がなく、総当たり・メール爆撃に弱い
- 該当: src/app/actions/auth.ts:18 / src/app/actions/auth-tokens.ts:64
- 指摘: ログイン失敗時のメッセージを統一している点、リセットでユーザー有無を返さない点は良いです。一方で、ログイン試行・パスワードリセット要求・招待再送に対する回数制限が見当たりません。攻撃者がログインを連続試行したり、登録済みメールアドレス宛にリセットメールを大量送信したりできます。
- 提案: IP単位とアカウント単位の両方で制限してください。例: ログインは「同一IP 10分20回」「同一メール 10分5回」、リセットは「同一メール 1時間3回」、招待再送は管理者操作でも「同一ユーザー 10分1回」程度。上限到達時は成功/失敗の詳細を増やさず、一定時間待つ案内にします。
- 根拠: `login()` は入力後すぐ `verifyCredentials()` を呼び、失敗しても記録・遅延・ロックを行っていません（src/app/actions/auth.ts:18-33）。`forgotPasswordAction()` もユーザーが存在すれば毎回トークン作成とメール送信へ進みます（src/app/actions/auth-tokens.ts:64-79）。

## R-03 〔重要度: 中〕 パスワード変更・ログアウト後に既発行JWTを失効できない
- 該当: src/auth/session.ts:14 / src/app/actions/auth-tokens.ts:100
- 指摘: JWT は7日有効で、ログアウトはブラウザ側のCookie削除のみです。パスワードリセット後も既存の別端末セッションを失効する仕組みが見当たりません。端末紛失やCookie流出が起きた場合、期限切れまでアクセスが続く可能性があります。
- 提案: ユーザーに `sessionVersion` または `passwordChangedAt` を持たせ、JWTにその値を入れて検証時にDBと照合してください。ログアウトを全端末失効にしたい場合はセッションテーブル方式も候補です。少なくともパスワードリセット完了時は既存セッションを無効化する設計にすると安心です。
- 根拠: Cookieは `maxAge` 7日で保存され（src/auth/session.ts:14-38）、`getCurrentUser()` はユーザー存在だけを確認しています（src/auth/session.ts:56-60）。パスワードリセット時はパスワード更新と新セッション作成のみで、過去JWTを無効化する状態更新がありません（src/app/actions/auth-tokens.ts:100-105）。

## R-04 〔重要度: 中〕 アップロードAPIに容量・回数・総量の濫用対策が足りない
- 該当: src/app/api/upload/route.ts:35
- 指摘: アップロードはログイン必須、種類制限、ランダムファイル名、1ファイル上限があり、基本設計は良いです。ただし、ログイン済みアカウントが短時間に多数アップロードした場合の回数制限や、ユーザー別・全体の総容量上限が見当たりません。特に動画は1本200MBまで許可されているため、ディスク枯渇やバックアップ肥大化のリスクがあります。
- 提案: ユーザー単位の「時間あたりアップロード回数」、日次アップロード容量、全体ディスク使用量の警告を入れてください。最低限、Nginx/PM2/監視スクリプトで `public/uploads` とDBバックアップ容量を定期確認し、閾値を超えたら店主に通知する運用を用意するとよいです。
- 根拠: `POST()` は認証、MIME、単体サイズの確認後に保存しますが、連続回数・ユーザー別総量・全体総量の確認がありません（src/app/api/upload/route.ts:35-107）。動画上限は200MBです（src/app/api/upload/route.ts:28-31）。

## R-05 〔重要度: 中〕 iframe許可は妥当だが、sandbox/CSP/許可属性をもう一段絞る余地がある
- 該当: src/lib/sanitize.ts:23
- 指摘: iframe は YouTube と Spotify に限定され、Spotify は `/embed/` のみに絞られているため、現在の実装は大きく危険ではありません。ただし `sandbox` は付いておらず、サイト全体の Content-Security-Policy も見当たりません。埋め込み先が侵害・仕様変更された場合の影響範囲をさらに狭める防御層がありません。
- 提案: 互換性確認のうえ、`sandbox="allow-scripts allow-same-origin allow-presentation"` など最小権限でプレイヤーが動くか検証してください。難しければ、まずHTTPヘッダーで `Content-Security-Policy` を追加し、`frame-src` を YouTube/YouTube-nocookie/Spotify のみに限定するだけでも効果があります。`allow` 属性もエディタ側が出す既定値に寄せ、投稿HTMLから自由に広げられないよう固定変換する案があります。
- 根拠: iframe は許可タグに含まれ、属性として `allow` も通ります（src/lib/sanitize.ts:23-31）。許可ホストとSpotifyの追加チェックはあります（src/lib/sanitize.ts:37-67）が、sandboxやCSPの設定は確認できませんでした。

## R-06 〔重要度: 中〕 プロフィール等の外部URLにスキーム検証がなく、危険/壊れたリンクが公開される余地がある
- 該当: src/app/actions/profile.ts:20 / src/app/actions/users.ts:30
- 指摘: 書き手プロフィールの Instagram/X/YouTube/Webサイト URL は文字列として保存されていますが、`https://` などの許可スキーム・ホスト・長さの検証が見当たりません。Reactのリンク描画で即XSSになる可能性は高くないものの、`javascript:` や不正なURL、意図しないプロトコルが公開プロフィールに入る余地があります。
- 提案: 保存時に URL パーサーで検証し、公開リンクは `http:` / `https:` のみにしてください。SNS欄は可能ならホストも `instagram.com`、`x.com`、`youtube.com` などに限定します。表示側でも外部リンクには `rel="noopener noreferrer"` を付ける方針に統一してください。
- 根拠: `updateMyProfileAction()` は各URLを trim して保存するだけです（src/app/actions/profile.ts:20-45）。管理者のユーザー編集でもURL項目は同様に readForm で文字列化されています（src/app/actions/users.ts:30-43）。

## R-07 〔重要度: 中〕 連載ページのSEOメタ情報が薄く、「三十年商店」検索後の見つけやすさを少し損ねる
- 該当: src/app/(public)/series/[slug]/page.tsx:47
- 指摘: 記事ページは title/description/canonical/OGP が入っていますが、連載ページは title のみです。検索結果に連載ページが出たとき、どんな書き手・どんな日記の一覧かが伝わりにくく、検索エンジンにもページの主題を渡しきれていません。
- 提案: 連載ページにも `description`、`alternates.canonical`、`openGraph` を追加してください。例: `「{連載名}」は三十年商店の連載日記です。最新の日記と過去の記事一覧を読めます。`。可能なら書き手名やリード文も短く含めると、読み手が検索結果から選びやすくなります。
- 根拠: `generateMetadata()` は category が見つかった場合に `{ title: category.name }` のみを返しています（src/app/(public)/series/[slug]/page.tsx:47-56）。一方、記事ページは説明文や canonical を設定済みです（src/app/(public)/posts/[slug]/page.tsx:60-93）。

## R-08 〔重要度: 低〕 sitemapの連載URLが slug ありの連載だけで、slugなし連載が将来漏れる
- 該当: src/app/sitemap.ts:31
- 指摘: sitemap は固定ページ、連載ページ、全公開記事を出しており方向性は良いです。ただし連載ページは `slug` があるものだけに絞っています。現在全連載にslugがあるなら実害はありませんが、将来 slug 未設定の連載ができると、画面上は `/series/{id}` で表示できるのに sitemap から漏れます。
- 提案: 表示側のルールと合わせて、`slug ?? id` で sitemap に載せるとズレが減ります。あわせて連載の `lastModified` を常に現在時刻にするのではなく、該当連載の最新記事日時にできるとより正確です。
- 根拠: sitemap の連載生成は `.filter((c) => c.slug)` 後に `/series/${slug}` だけを出します（src/app/sitemap.ts:31-40）。表示側は `category.slug ?? category.id` をベースパスにしています（src/app/(public)/series/[slug]/page.tsx:89-90）。

## R-09 〔重要度: 低〕 本番のrobots/sitemap実体確認を定期チェック化したい
- 該当: src/app/robots.ts:7 / src/app/sitemap.ts:18
- 指摘: コード上は `SITE_INDEXABLE=true` のとき robots が allow になり、sitemap も生成されます。移行ログにも本番確認済みの記録があります。ただし robots/sitemap は本番環境変数やビルドタイミングに依存するため、今後のデプロイで誤って `Disallow: /` や別ドメインURLに戻ると、「三十年商店」で検索した人が見つけにくくなります。
- 提案: デプロイ後チェックに `curl https://30nen.com/robots.txt` と `curl https://30nen.com/sitemap.xml | head` を固定項目として入れ、`Disallow: /` がないこと、`https://30nen.com/` のURLだけが出ることを機械的に確認してください。Google Search Console への sitemap 送信状況も運用メモに残すとよいです。
- 根拠: robots は `isIndexable()` に依存します（src/app/robots.ts:7-15）。sitemap の絶対URLは `siteUrl()` に依存します（src/app/sitemap.ts:18-52）。今回のレビュー環境ではネットワーク制限により本番URLの直接取得は未確認です。

## R-10 〔重要度: 低〕 記事本文の検索性はあるが、サイト内検索はHTML混じり照合でノイズが出る余地がある
- 該当: src/db/articles.ts:462
- 指摘: サイト内検索はタイトル・本文・抜粋をAND検索でき、読み手が過去記事を探す入口として機能しています。一方で本文はHTMLのままLIKE検索しているため、リンクURL・属性・埋め込みHTMLに含まれる文字列が検索ヒットする可能性があります。通常利用では大きな問題ではありませんが、「読みたい言葉」で探したときにノイズが混じる余地があります。
- 提案: すぐ直す必要は低いですが、将来的には保存時に `searchText`（タグ除去済み本文）を持つか、SQLite FTS5 を使うと精度と速度が上がります。少なくとも検索結果には本文抜粋を表示すると、読み手が目的の記事か判断しやすくなります。
- 根拠: `searchFilters()` は `articles.content` をHTMLのまま `LIKE` しています（src/db/articles.ts:462-471）。コメントにも「本文はHTMLのまま照合」と明記されています。
