# レビュー指摘 2026-06-22（第3回）

レビュー担当: Codex
対象: outbox/2026-06-22_question-01.md

## 総合判定

**本番の置き場所として Xサーバー VPS を第一候補にする判断は妥当。**

ただし、**2026-06-22 のお試し期限に合わせてこのまま本契約する必要性は低い**と見ます。公開が7月下旬から8月末で、残作業の中心が移行スクリプト・全件リハーサル・運用設計であるなら、今日の合理的判断は「いったん失効させ、公開前リハーサル時に再契約して建て直す」です。

理由は、すでに「Xサーバー VPSで動くか」という最大の技術的不確実性は実機検証で解消済みであり、今から本契約しても得られる主な価値は「同じ環境を保持できる安心感」に限られるためです。一方で、本契約すると本番前からOS更新・セキュリティ・バックアップ・監視の責任が始まります。

## R-01 〔重要度: 高〕 今日の本契約は「技術判断」ではなく「運用開始」の判断になる

- 該当: 本契約判断全体
- 指摘: Xサーバー VPSを使う判断と、今日から有料運用を始める判断は分けるべきです。前者は妥当ですが、後者はまだ必須ではありません。
- 提案: 今日は契約せず失効でよい。ただし、再構築手順、Nginx設定、PM2設定、環境変数、DB/uploads配置、デプロイ手順を必ず文書化してから失効させる。
- 根拠: 本番切替が少し先で、現時点のサーバーは公開サービスとして常時稼働させる必要がないため。月額費用よりも「本番前からサーバーを持ち続ける心理的・運用的負債」の方が重い。

## R-02 〔重要度: 高〕 30年運用の最大リスクはVPS選定ではなく保守体制

- 該当: VPSの運用・保守負担
- 指摘: Xサーバー VPSそのものより、専任インフラ担当がいない状態でOS更新、Node更新、証明書更新、障害対応、バックアップ復旧を継続できるかが支配的なリスクです。
- 提案: 本番採用条件として、最低限次をGo/No-Goに入れる。
  - 自動バックアップ、または別ストレージへの毎日バックアップ
  - SQLite DBとuploadsの復旧リハーサル
  - OS/Node/アプリ更新の月次手順
  - サーバー再起動後の自動復帰確認
  - 障害時に誰が何を見るかの短い手順書
- 根拠: 20名以上が日々書く公開日記サイトでは、性能限界よりも「壊れた時に戻せるか」が信用に直結するため。

## R-03 〔重要度: 中〕 SQLite単一ファイルは現時点では妥当だが、バックアップ設計が前提

- 該当: SQLite / better-sqlite3 / data/30nen.db
- 指摘: 20名以上が1日数回投稿する程度なら、SQLiteは十分現実的です。記事数が数万件になっても、読み書きの性質から見て直ちにMySQL/PostgreSQLが必要とは言えません。ただし、単一ファイルであるぶん、バックアップと復旧の手順が未熟だと単一障害点になります。
- 提案: DB方式は維持でよい。移行判断ラインは「書き込み待ちが実測で問題化する」「全文検索や集計が重くなる」「管理機能が複雑化する」「複数台構成が必要になる」のいずれかが出た時でよい。
- 根拠: 現在の利用プロファイルは高並行書き込みではないため、DBサーバー導入は今の複雑さを増やす可能性が高い。

## R-04 〔重要度: 高〕 バックアップは「取る」ではなく「戻せる」までが本番条件

- 該当: バックアップ / ロールバック / DR
- 指摘: 単一VPS構成では、DB、uploads、環境変数、Nginx設定、PM2設定のどれかを失うと復旧が詰まります。バックアップの存在だけでは不十分です。
- 提案: 本番前に、空のVPSへ次を使って復元できることを一度試す。
  - SQLite DBファイル
  - uploads一式
  - `.env`相当の秘密情報
  - Nginx設定
  - PM2設定
  - デプロイ手順書
- 根拠: 長期運用では「サーバーが壊れないこと」ではなく「壊れても戻せること」を前提にした方が安全です。

## R-05 〔重要度: 中〕 Xサーバー VPSから裏返る可能性は低いが、ゼロではない

- 該当: 代替案比較
- 指摘: 判断が裏返る主なシナリオは、技術性能ではなく運用負担・バックアップ・障害対応です。
- 提案: 裏返り確率の目安は次の通り。
  - 技術的に動かない: 低い（実機検証済み）
  - SQLite性能不足: 低い
  - ストレージ不足・画像容量問題: 中
  - VPS保守が負担になり継続困難: 中〜高
  - 本番前の移行リハーサルで想定外の手戻り: 中
- 根拠: 実機でNext.js/PM2/Nginx/SQLiteが動いたため、残る大きな不確実性は実データ量と運用体制に寄る。

## R-06 〔重要度: 中〕 安価なマネージド寄り折衷案は「バックアップだけ外に出す」

- 該当: コストゼロ方針 / マネージド寄り案
- 指摘: 月額SaaSゼロを厳密に守ると、保守負担がVPS側に寄ります。アプリやDBをPaaS化するより、まずはバックアップ先だけ外部化するのが最小の折衷です。
- 提案: DB/uploadsのバックアップを、別サーバー、オブジェクトストレージ、または既存契約の別領域へ逃がす。アプリ本体はVPSのままでよい。
- 根拠: 一番避けたい事故は「VPSごと消えた時に全データを失うこと」であり、ここだけ外部化すると費用対効果が高い。

## R-07 〔重要度: 中〕 失効前に回収すべき成果物がある

- 該当: 今は失効→お披露目前に建て直し
- 指摘: 失効自体は合理的ですが、実機検証で得た設定情報を失うと再構築コストが上がります。
- 提案: 失効前に以下をリポジトリまたは安全なメモに残す。
  - OSバージョン、Nodeバージョン、npmバージョン
  - Nginx server block
  - PM2 ecosystem設定または起動コマンド
  - uploads配置と権限
  - `client_max_body_size` など調整値
  - デプロイ手順
  - 本番化TODO
- 根拠: 「再構築できる」は、手順が残っていて初めて本当に強い判断材料になるため。

## 結論

Xサーバー VPSは、本番候補としてそのまま進めてよいです。致命的な見落としは見当たりません。

一方で、今日このまま本契約することは推奨しません。現時点では「サーバーを保持する価値」より「本番前から運用責任を始めてしまう重さ」の方が大きいです。

おすすめは次です。

1. 今日中に実機設定とデプロイ手順を回収する。
2. お試しVPSはいったん失効させる。
3. 移行スクリプトと全件リハーサルの準備をローカル中心に進める。
4. 公開前リハーサルの段階でXサーバー VPSを再契約する。
5. 本番化前に「バックアップから復旧できる」ことを確認してからGo判定する。

例外として、今後1〜2週間のうちにXサーバー上で全件移行リハーサルや投稿者テストを継続する予定が具体的にあるなら、1か月だけ本契約する選択も合理的です。その場合も「本番サーバー確保」ではなく「検証環境の延長」と位置づけるのがよいです。
