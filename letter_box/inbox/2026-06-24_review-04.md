## 総合判定

**移行の「運ぶ道具」はかなり前進しています。このまま進めて大丈夫です。**

ただし、2026年7月下旬切替を本当にGoにするには、まだ条件つきです。特に危ない山は、次の4つです。

1. 旧WordPressの記事URLが、新サイトでそのまま開くか、または301転送されるか。
2. 画像を原寸のまま大量に運んでしまわないか。
3. バックアップから本当に復旧できるか。
4. 投稿者さんが「練習用」と「本番投稿」を取り違えず、初回ログインから画像つき投稿まで迷わず進めるか。

総合判断は、**「一部条件を締めて進める」**です。7月下旬は努力目標のまま走ってよいですが、全件リハーサル、旧URL確認、復旧テスト、本番相当ビルド、書き手マニュアル配布が大きく残るなら、8月末へ寄せる判断が安全です。

## R-01 〔重要度: 高〕 旧記事URLが切れる可能性がまだ残っている

- 該当: 記事詳細URL、SEO、既存リンク維持
- 指摘: 新サイトの記事リンクは `/posts/{slug}` または `/posts/{id}` になっています。一方、旧サイト側には `/oshirase/2025/07/23/12729` のようなカテゴリ・日付・IDを含むURLが存在します。slugを保持するだけでは、読者のブックマーク、検索結果、サイト内の古いリンクが切れる可能性があります。
- 根拠:
  - `src/components/public/article-card.tsx` では記事リンクが `/posts/${article.slug}`。
  - `src/app/(public)/posts/[slug]/page.tsx` は `/posts/[slug]` のページ。
  - `src/app/(public)/about/page.tsx` には旧形式らしき `/oshirase/2025/07/23/12729` へのリンクあり。
  - `migration/data-migration-plan.md` でも 301、sitemap、robots、canonical、OGP は未チェック項目。
- 提案:
  - 切替前に、旧URL 100件程度をサンプル抽出し、新サイトで「そのまま開く」または「正しく301転送される」ことを確認する。
  - 旧URL形式が複数ある場合は、Next.js側またはNginx側で301リダイレクトを用意する。
  - `sitemap.xml`、`robots.txt`、canonical、記事OGPも本番Go条件に入れる。

## R-02 〔重要度: 高〕 バックアップは設計済みだが、復旧実演がまだ

- 該当: VPS運用、SQLite、uploads、`.env.local`、Nginx、PM2
- 指摘: バックアップ対象はよく整理されています。ただし「取る」だけでは本番の守りとしては不十分で、空のVPSへ戻せることを一度確認する必要があります。
- 根拠:
  - `docs/deploy-notes.md` で DB、uploads、秘密設定、Nginx/PM2 がバックアップ対象として明記されている。
  - 同ファイルの本番化TODOにも「空のVPSへ実際に復元できるか1回試す」とある。
- 提案:
  - 本番Go条件に「復旧リハーサル合格」を明記したままでよい。
  - 復旧対象は SQLite DB、`public/uploads/`、`.env.local`、Nginx設定、PM2設定、デプロイ手順。
  - 切替後に戻す判断基準と、戻した場合の投稿者さん向け連絡文も事前に作る。

## R-03 〔重要度: 中〜高〕 移行時の画像はまだ「軽くして運ぶ」になっていない

- 該当: `scripts/migrate-articles.ts`、画像容量、VPSストレージ
- 指摘: 新規アップロードは長辺1600pxに縮小される作りで安心です。一方、移行スクリプトの `--download` は現行WordPressの画像を取得して、そのまま `public/uploads/` に保存しています。現行画像が大きい場合、移行後の容量が想定より膨らむ恐れがあります。
- 根拠:
  - `src/app/api/upload/route.ts` は通常アップロード時に sharp で長辺1600pxへ縮小。
  - `scripts/migrate-articles.ts` の `--download` は `fetch` 後にそのまま `writeFileSync`。
- 提案:
  - S4全件リハーサル前に、移行画像にも長辺1600px縮小を入れるか判断する。
  - 原寸保持が必要な記事があるか、SAKIさん判断で方針を決める。
  - 最低限、全件リハーサルで総容量、所要時間、画像欠落数をレポート化する。

## R-04 〔重要度: 中〕 本番相当ビルド成功はまだGo条件に残す

- 該当: `npm run build`、Next.js 16 / Turbopack、本番VPS
- 指摘: ローカルでは `npm run build` が Turbopack 内部エラーで失敗しました。エラー内容は「ポートに bind できない」で、作業環境の制限由来に見えます。コード不具合とは断定しませんが、本番相当VPSでのビルド成功は必須です。
- 提案:
  - Xサーバー VPSを再契約したら、早い段階で `npm ci` → `npm run build` → PM2起動 → Nginx経由確認まで通す。
  - ここが通らない状態では切替日を確定しない。

## R-05 〔重要度: 中〕 本文HTMLの安全対策は入っているが、画像URL許可は少し広め

- 該当: `src/lib/sanitize.ts`
- 指摘: 本文HTMLは保存時・表示時にサニタイズされており、基本の守りは入っています。一方で、本文中の画像URLとして `http`、`https`、`data` が許可されています。信頼できる投稿者だけなら大きな事故にはなりにくいですが、長期運用では少し締めてもよいです。
- 提案:
  - 将来的には、本文画像は `/uploads/` 配下を基本にする。
  - 外部画像や data URL を許す必要があるか、運用方針として決める。

## R-06 〔重要度: 良い点〕 移行の二重取り込み防止はかなり強くなっている

- 該当: DBスキーマ、移行スクリプト
- 評価: `articles.wp_id`、`users.wp_id`、`categories.wp_term_id` に一意制約が入り、スクリプト側だけでなくDB側でも二重取り込みを止められます。これは前回レビューからの大きな改善です。
- 補足: SQLiteでは `NULL` の unique は複数許容されるため、新規投稿の `wp_id = NULL` は問題になりにくいです。

## 投稿者さんが戸惑いそうなポイント

### W-01 〔最重要〕 「練習用」と「本番投稿」の取り違え

切替前の新システムは練習用、本物の記事はWordPressへ、というルールは安全です。ただし、投稿者さん側から見ると「新しい投稿画面に入れたから、もうここに書けばいい」と誤解しやすいです。

対策:
- 練習用サイトの管理画面上部に、切替前だけ目立つ表示を出す。
- 文言例: **「ここは練習用です。正式切替までは、本番の日記は今までどおりWordPressへ投稿してください。」**
- アナウンス文にも、同じ表現を繰り返し入れる。

### W-02 〔高〕 自動保存の意味

新規・下書きは10秒ごとに自動保存されます。一方、公開済みの記事は自動保存されません。これは安全な設計ですが、投稿者さんには少しわかりにくいです。

手順書に入れること:
- 新しく書いている途中は、自動で下書き保存される。
- 公開済みの記事を直したときは、最後に必ず **「投稿する」** を押す。
- 「自動保存しました」と出ても、公開したい場合は **「投稿する」** が必要。

### W-03 〔高〕 「下書き保存」と「投稿する」の違い

ボタン名は自然ですが、ITに不慣れな方には「どちらを押せば公開されるのか」が不安になりやすいです。

手順書に入れること:
- **下書き保存**: まだ公開されない。あとで続きが書ける。
- **投稿する**: サイトに公開される。
- 画像つきスクショで、2つのボタンに印をつける。

### W-04 〔中〕 アイキャッチ未設定の確認ダイアログ

「投稿する」を押したとき、アイキャッチ画像が未設定だと確認が出ます。これは親切ですが、突然出ると「エラーかも」と不安になります。

手順書に入れること:
- 写真なしでも投稿できる。
- 写真なしでよければ「OK」。
- 写真を入れたい場合は「キャンセル」して画像を選ぶ。

### W-05 〔中〕 連載選択

担当連載が1つだけなら自動で選ばれます。複数担当、または担当未登録の場合は選択が必要です。ここで迷うと投稿できません。

対策:
- 本番アカウント作成時に、全員の担当連載を事前に設定しておく。
- 手順書では「ふつうは自分の連載が自動で入っています」と説明する。
- 複数担当の人だけ、連載欄の選び方を別枠で説明する。

### W-06 〔中〕 写真アップロードの失敗

スマホ写真は基本そのまま上げられますが、40MB超、非対応形式、通信不安定では失敗し得ます。海外在住の方は回線差もあります。

手順書に入れること:
- 使える画像: JPEG、PNG、GIF、WebP。
- うまくいかない時は、1枚ずつアップロードする。
- 通信が弱い時はWi-Fiで試す。
- 写真が重くても、サイト側で自動で軽くする。

### W-07 〔中〕 ログインできない時の連絡先

投稿者さんにとって最大の不安は、機能より「入れない」「パスワードがわからない」「誰に聞けばいいかわからない」です。

対策:
- 初回案内に、問い合わせ先を1つだけ明記する。
- 日本語・スペイン語で同じ連絡先を書く。
- パスワード再発行の簡単な運用を決めておく。

### W-08 〔中〕 日本時間と海外時間

公開日時欄は日本時間の前提です。海外在住の投稿者さんが使う場合、予約投稿や日付修正で混乱しやすいです。

手順書に入れること:
- 日付を空欄にして「投稿する」なら、今すぐ公開。
- 日付を入れる場合は日本時間。
- よくわからなければ空欄でOK。

## 手順書に入れるとよい構成

投稿者さん向けマニュアルは、機能説明より「迷わず1本出す」ことを優先するのがよいです。

おすすめ構成:

1. ログインする
2. 新しい日記をかく
3. タイトルを書く
4. 本文を書く
5. 写真を入れる
6. 下書き保存と投稿する
7. 公開後に直す
8. 困った時の連絡先

日本語版・スペイン語版とも、文章は短く、スクショ中心がよいです。操作動画もあると、言葉の壁をかなり越えられます。

## Go/No-Goに追加したい確認

切替前に、次が揃っていれば安心度が上がります。

- [ ] 全件リハーサルで、記事数・著者・連載・日時・画像欠落が確認済み。
- [ ] 移行画像の容量と縮小方針が決定済み。
- [ ] 旧URLサンプルが新サイトで開く、または301転送される。
- [ ] `sitemap.xml`、`robots.txt`、canonical、記事OGPが用意済み。
- [ ] 本番相当VPSでビルド・起動・画像アップロード・ログイン確認済み。
- [ ] 空のVPSへバックアップから復旧できることを確認済み。
- [ ] 投稿者さん向けマニュアルとアナウンスが日本語・スペイン語で配布可能。
- [ ] 練習用画面に「本番投稿はまだWordPressへ」の表示がある。
- [ ] パスワード配布・ログイン不可時の連絡先が決まっている。

## 結論

サイト側は、以前よりかなり堅くなっています。移行キーの一意制約、サニタイズ、所有者チェック、画像アップロード縮小、自動保存など、重要な守りは入っています。

ただし、公開サイトとしての信用を守る観点では、最後に残っているリスクはコードの細部よりも、**URL・画像・復旧・人の移行**です。

次に作る投稿者さん向け手順書では、機能を全部説明するより、まず「ログインして、日記を書いて、写真を入れて、投稿する」までを、迷わずできる短い道にするのがよいと思います。特に「練習用」「自動保存」「公開済み記事の保存」「写真なし投稿」「困った時の連絡先」は、書き手さんの不安を先回りして減らせるポイントです。
