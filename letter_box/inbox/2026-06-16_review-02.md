# 30nen.com Migration Risk Review for Coding Agent

作成日: 2026-06-16  
対象: 30nen.com（三十年商店） WordPress から Next.js 自前システムへの移行  
目的: 別エージェントが次の実装・移行作業に入る前に、スケジュールと技術リスクを共有する。

## 1. 総合判定

2026年7月下旬切替は不可能ではないが、かなり強気。

「一部修正して進める」が妥当。ただし、実務上の安全な本命日は 2026年8月中旬から8月末 と見る。

理由:

- 初回の Xサーバーデプロイが未実施。
- 全件記事移行スクリプトが未着手。
- 約7,790記事ぶんの画像容量・転送時間が未計測。
- 書き手20名以上のオンボーディングがまだ始まっていない。
- バックアップとロールバック手順が明文化されていない。
- サイト本体の公開ページは進んでいるが、全件実データ入りでの品質確認がまだない。

7月下旬は「すべてが一発でうまくいく」前提に近い。目標として走るのはよいが、Go/No-Go 条件を厳しく置くこと。

## 2. クリティカルパス

### 2-1. Xサーバー本番相当デプロイ

最重要。

Next.js 16 + React 19 + SQLite + PM2 + Nginx + uploads 永続フォルダ + SSL を、Xサーバー上で安定稼働させる必要がある。

本番切替前に最低限確認すること:

- `npm run build` が本番相当環境で成功する。
- PM2 で Next.js が再起動後も復帰する。
- Nginx 経由で公開ページ、管理画面、画像アップロードが動く。
- `public/uploads/` 相当の永続フォルダがデプロイで消えない。
- SQLite DB ファイルの保存場所、権限、バックアップ方法が決まっている。
- SSL 証明書がテスト用アドレス・本番ドメインで問題なく使える。

### 2-2. 全件記事・画像移行

約7,790記事と画像の移行は、必ず早期に「全件」で試すこと。

リハーサルで測るべきもの:

- WordPress 側公開記事数と新DB取り込み件数。
- 画像総容量。
- 画像ダウンロード所要時間。
- 欠落画像数。
- 文字化けの有無。
- 著者・連載の対応漏れ。
- slug の一致。
- 公開日時と並び順。

### 2-3. 投稿者20名以上のオンボーディング

マニュアル配布だけでは足りない。

切替前の最低条件:

- 全員分のアカウントが作成済み。
- 全員にログイン情報が届いている。
- 主要メンバーがログイン済み。
- 複数名が画像付き投稿を試している。
- パスワード紛失時の対応が決まっている。
- 日本語・スペイン語の案内文がある。
- 質問窓口が1つに決まっている。

## 3. Go/No-Go 判定条件

現行計画では 2026年7月6日ごろを判断ポイントとしている。これは良いが、条件を厳しくすること。

2026年7月6日までに以下が揃っていれば、7月下旬切替に進んでよい。

- Xサーバー上のテストURLで新サイトが動いている。
- 本番相当環境でビルド成功済み。
- WordPress全件データを一度取り込めている。
- 画像の総容量・転送時間・欠落数が把握できている。
- 記事詳細、連載別、月別アーカイブが実データで見られる。
- 著者対応表と連載対応表が埋まっている。
- 本番DB初期化手順が決まっている。
- 切替当日の手順書がある。
- ロールバック手順がある。
- 書き手向けアナウンスとマニュアルが配布可能な状態。

1つでも大きく欠ける場合は、2026年8月末切替へ延期する判断を推奨する。

## 4. コード・DB上の注意点

### 4-1. `wp_id` にDB側の一意制約を追加する

現状、`articles.wp_id` は列として存在するが、一意制約がない。

移行スクリプト側で `wp_id` を見て重複スキップするだけでは不十分。バグや並列実行で二重取り込みが起きてもDB側で止められるよう、`wp_id` に unique index を追加すること。

推奨:

- `articles.wp_id` に unique index。
- `users.wp_id` にも必要なら unique index。
- `categories.wp_term_id` にも必要なら unique index。

注意:

- SQLite では `NULL` は unique index 内で複数許容されるため、新規投稿の `wp_id = NULL` は問題になりにくい。

### 4-2. slug 維持だけでSEOは完了しない

旧WordPressのURL構造と新Next.jsのURL構造が完全一致するか確認すること。

必要な確認:

- 旧記事URLが新記事URLでそのまま開くか。
- 一致しない場合は 301 リダイレクトを用意する。
- `sitemap.xml` を生成する。
- `robots.txt` を用意する。
- canonical URL を設定する。
- OGP title / description / image を記事ページで確認する。
- 404ページと検索エンジン向け挙動を確認する。

### 4-3. ビルド確認

このレビュー時点で `npm run build` を試したが、作業環境側の制限により Next/Turbopack が内部エラーになった。

これはコード不具合とは断定しない。ただし、本番相当環境でのビルド成功確認は最優先タスク。

## 5. 移行スクリプトに求める仕様

必須:

- 何度実行しても壊れない冪等設計。
- `wp_id` による重複スキップ。
- 最終結果として、取り込み件数・スキップ件数・エラー件数を表示。
- エラー記事の `wp_id` と原因をログに残す。
- 画像ダウンロード失敗を記事全体の失敗と分けて記録。
- 本文HTMLは保持しつつ、画像URLを書き換える。
- 著者対応表・連載対応表に存在しないIDが出たら止めるか、明示的に隔離する。
- 移行前後の件数照合レポートを出す。

望ましい:

- dry-run モード。
- 画像だけ再取得するモード。
- 既存記事を上書きするかスキップするかのモード切替。
- 途中失敗後に再開しやすいログ。

## 6. ロールバック手順に必ず入れること

切替前に明文化する。

- 切替前の WordPress は削除しない。
- WordPress は数週間読み取り可能な状態で温存する。
- 新システムの SQLite DB を切替前に丸ごとバックアップする。
- uploads フォルダも切替前にバックアップする。
- DNS を戻す手順を明記する。
- DNS TTL を切替数日前に短くする。
- 切替後何時間以内なら戻すか、判断基準を決める。
- 戻した場合に書き手へ送る連絡文を用意する。

## 7. 投稿者移行の実務リスク

並行期間のルール自体は良い。

本物の投稿は切替まで WordPress に集め、新システムは練習用にする方針は、データの出どころが1つになり安全。

ただし、次の事故が起きやすい。

- 書き手が練習用の新システムに本番記事を書いてしまう。
- 切替直前に WordPress に投稿された記事を差分移行で取りこぼす。
- パスワードが届かない、またはログインできない。
- 画像アップロードが端末・回線・ブラウザ差で失敗する。
- 日本語以外の書き手が案内を理解できない。

対策:

- 練習用画面には、切替前だけ「ここは練習用。本番投稿はWordPressへ」の表示を出す。
- 切替当日は WordPress への最終投稿締切時刻を明示する。
- 差分移行後、最新10件を WordPress と新システムで目視照合する。
- 日本語・スペイン語の短い案内を用意する。
- 初回ログイン失敗時の連絡先を1つにする。

## 8. 推奨される次の作業順

1. Xサーバーのテストデプロイを最優先で行う。
2. 本番相当環境でビルド成功を確認する。
3. `wp_id` など移行キーの unique index を追加する。
4. 著者対応表・連載対応表のひな形を作る。
5. WordPress全件エクスポート方式を確定する。
6. 移行スクリプトを作る。
7. 手元で全件リハーサルを行う。
8. Xサーバー上で全件リハーサルを行う。
9. 画像容量、欠落、表示崩れ、件数をレポート化する。
10. 書き手向けマニュアルと初回ログイン導線を作る。
11. Go/No-Go 判定を行う。
12. 切替日を確定する。

## 9. 結論

7月下旬切替を目標に作業を進めるのはよい。ただし、2026年7月6日時点で本番相当デプロイと全件リハーサルが完了していなければ、2026年8月末へ延期することを推奨する。

この判断は弱気ではなく、20名以上の書き手と公開日記サイトの信用を守るための現実的な安全策。
