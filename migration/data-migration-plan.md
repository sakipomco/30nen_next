# 記事データ移行プラン（準備スケジュール・v1）

作成日: 2026-06-16 ／ 対象: 30nen.com（WordPress）の公開記事 **約7,790件** を新システムへ移す

> このファイルは、記事データ移行を軸に、**①記事移行の準備（技術）／②書き手へのアナウンスとお試し期間／③本移行・切替**を
> **1枚の通しスケジュール**にまとめたものです（`schedule.md` を、記事移行を中心に日付へ落とし込んだ実行版）。
> Claude Code の作業メモ兼、SAKIさんへの「何を・いつ・誰が」一覧として使います。
>
> 用語メモ
> - **移行（いこう／migration）** … 古いシステムから新システムへデータを引っ越すこと。
> - **エクスポート** … データを外に書き出すこと。**インポート** … 書き出したデータを取り込むこと。
> - **スクリプト** … 決まった作業を自動でやる小さなプログラム。
> - **リハーサル移行** … 本番の前に、手元のパソコンで一度通しでやってみる予行演習。

## 0. 前提（確定ずみ）

| 項目 | 決めたこと |
|------|-----------|
| 切替の目標時期 | **7月下旬**（`30nen.com` を新サイトに向ける日。本ファイルはこれを基準に逆算） |
| 運ぶもの | **公開記事のみ**（約7,790件）。本文HTML・タイトル・公開日時・著者・連載・記事内画像 |

> 用語メモ
> - **slug（スラッグ）** … 記事ごとのアドレス末尾（例: `30nen.com/`**`koharu-biyori`**）。現行サイトの slug は日本語をURL用に変換した形（URLエンコード）なので、移行時もそのまま引き継ぐ。

## 1. 準備の全体像（5つの仕込み）

記事を運ぶ前に、土台になる「5つの仕込み」を用意します。**S1・S2 は SAKIさんの作業**、**S3〜S5 は Claude Code の作業**です。

```
 [S1 著者対応表] ──┐
                   ├──▶ [S3 移行スクリプト] ──▶ [S4 リハーサル移行＋点検] ──▶ 本移行へ
 [S2 連載対応表] ──┘                              ▲
                                  [S5 画像の運び方] ┘
```

| 記号 | 仕込み | 担当 | これが無いと困ること |
|------|--------|------|--------------------|
| S1 | **著者対応表**（WP著者番号 ↔ 新システムの誰か） | SAKI（Claudeが下地を用意） | 記事の「書いた人」が正しくひもづかない |
| S2 | **連載(カテゴリ)対応表**（WPの連載 ↔ 新システムの連載） | SAKI＋Claude | 記事が正しい連載に入らない／未分類が出る |
| S3 | **移行スクリプト**（何度流しても安全＝冪等） | Claude Code | 自動で運べない |
| S4 | **リハーサル移行＋点検** | Claude Code | 本番で初めて不具合に気づく＝危険 |
| S5 | **画像の運び方**（本体ダウンロード＋URL書き換え） | Claude Code | 記事の写真が表示されない／リンク切れ |

> 用語メモ
> - **冪等（べきとう／idempotent）** … 同じ処理を何回流しても結果が壊れない性質。今回は「すでに運んだ記事は飛ばす」作りにする。判定には各記事に控える **`wp_id`（WordPress側の記事番号）** を使う（DB設計で確保ずみ）。

## 2. 仕込みの中身（S1〜S5）

### S1. 著者対応表（担当: SAKI／下地: Claude）
現行 WordPress は記事ごとに「書いた人＝**著者番号（数字）**」で記録しています。新システムは20名のアカウントを作り直すので、「**WP著者番号 ↔ 新システムの誰か**」をつなぐ一覧が要ります。

手順:
1. Claude が現行WPから **著者一覧（番号・表示名・メール・記事本数）** を読み取りだけで取得 → 表のひな形を作る。
2. SAKIさんが「この番号＝新システムのこの人」を埋める（兼ねて、その人の担当連載・使用言語も）。
3. この表を S3 のスクリプトが使う。

> メモ: 退会済み・もう投稿しない著者番号が出てくる可能性あり。その場合の扱い（記事は残すが著者は「元・書き手」にまとめる等）はひな形を見ながら相談。

### S2. 連載(カテゴリ)対応表（担当: SAKI＋Claude）
現行WPの連載（`wp_term_id`）と、新システムの `categories`（連載）を結びつけます。

手順:
1. 現行の連載構造は `reference/categories.json`（22件・親子: 度々の旅＞山陰編）で把握ずみ。
2. 新システム側に同じ連載を作成（`wp_term_id` 列に旧番号を控える＝突き合わせの鍵）。
3. スクリプトは記事の旧連載番号 → 新連載 を `wp_term_id` 経由で対応づける。

### S3. 移行スクリプト（担当: Claude Code）
- 入力: WordPressから書き出した公開記事の一式（本文HTML・タイトル・slug・公開日時・著者番号・連載番号・画像URL一覧）。
- 変換して `articles` テーブルへインポート。**`wp_id` で重複チェック**（すでにある記事は飛ばす＝冪等）。
- 著者は S1、連載は S2 の対応表を使ってひもづけ。
- 本文中の画像URLは S5 のルールで書き換え。

**スクリプトに必ず入れる仕様（レビュー反映）**
- **DB側にも重複防止の鍵をかける**: `articles.wp_id` に **unique index（一意制約）** を追加。スクリプトの判定に加え、バグや二重実行が起きてもDB自身が二重取り込みを止める（`users.wp_id`・`categories.wp_term_id` も同様に検討）。※SQLiteでは新規投稿の `wp_id = NULL` は複数あってもOK。
- **dry-run（お試し実行）モード**: DBに書かず「何件取り込む／飛ばす／エラーか」だけ表示。
- **エラーの記録**: 失敗した記事の `wp_id` と原因をログに残す。**画像ダウンロードの失敗は、記事本体の失敗とは分けて記録**（写真だけ後追いで直せるように）。
- **対応表に無いIDが出たら止める**（または明示的に隔離）。著者番号・連載番号が対応表に無いまま素通りさせない。
- **件数照合レポート**: 移行前（WordPressの公開記事数）と移行後（取り込めた件数）を最後に突き合わせて出力。
- **（あると望ましい）** 画像だけ再取得するモード／途中失敗から再開しやすいログ。

> 安全策: スクリプトは WordPress を**読み取りだけ**。書き込み先は新システムのDBのみ。現行サイトには一切触れない。

### S4. リハーサル移行＋点検（担当: Claude Code）
本番の前に、手元のパソコンで全記事を一度通しで流し、下のチェックリストで点検します。

**点検チェックリスト**
- [ ] 件数: WordPressの公開記事数（約7,790）と、取り込めた件数が合うか
- [ ] 文字化け: 日本語・スペイン語・英語まじりの記事が正しく表示されるか
- [ ] 画像: 本文の写真がすべて表示されるか（リンク切れ・抜けがないか）
- [ ] 連載: 各記事が正しい連載に入っているか（未分類が出ていないか）
- [ ] 著者: 「書いた人」が正しい人になっているか
- [ ] 公開日時: 並び順・日付が現行と一致するか
- [ ] slug: アドレスが現行と同じか（昔のリンクで開けるか）
- [ ] 親子連載: 「度々の旅＞山陰編」のような階層が崩れていないか

### S5. 画像の運び方（担当: Claude Code）
- 記事内の画像は現在 `https://30nen.com/wp-content/uploads/...` の**絶対URL**で本文に埋まっている。
- スクリプトで画像本体を**ダウンロード**し、新サイトの保存場所（`public/uploads/...`）へ配置。
- 本文中のURLを新サイトの住所に**自動で書き換え**。
- 注意: `public/uploads/` はGit管理外の**永続フォルダ**。デプロイで消えない扱いにする（`schedule.md`／HANDOFFの注意点と同じ）。

> 容量メモ: 約7,790記事ぶんの画像はそれなりの量になる見込み。リハーサル時に総容量を計測し、Xサーバーの空き容量で足りるか確認する（足りなければ縮小・サムネ方針を相談）。

## 5. 切替の安全装置（SEO・バックアップ・ロールバック）

### 5-1. SEO・旧リンク維持（slug以外にやること）
slug（アドレス末尾）を揃えるだけでは不十分。旧WordPressと新サイトでURLの形が完全一致するか確認する。

- [ ] 旧記事URLが、新サイトでそのまま開くか確認。
- [ ] 一致しない形があれば **301リダイレクト**（旧URL→新URLへ自動転送）を用意。
- [ ] `sitemap.xml`（検索エンジン向けの地図）を生成。
- [ ] `robots.txt`（クローラ向けの案内）を用意。
- [ ] **canonical URL**（正規URLの指定・重複扱いを防ぐ）を設定。
- [ ] 記事ページの **OGP**（SNS共有時のタイトル・説明・画像）を確認。
- [ ] 404ページ・存在しないページ番号の挙動を確認。

> 用語: **301リダイレクト**＝「この住所は新しい住所へ引っ越しました」と自動転送する仕組み。検索順位・既存リンクを引き継げる。

### 5-2. バックアップとロールバック（戻し方）
切替に失敗しても元へ戻せるよう、**切替前に**明文化しておく。

- [ ] **切替前のWordPressは削除しない**。数週間は読み取り可能な状態で温存。
- [ ] 切替直前に、新システムの **SQLite DB を丸ごとバックアップ**。
- [ ] 切替直前に、**uploads（画像）フォルダもバックアップ**。
- [ ] **DNSを元に戻す手順**を書いておく（＝公開アドレスをWordPressへ戻す）。
- [ ] **DNSのTTLを切替の数日前に短く**しておく（切替・切り戻しが速く反映される）。
- [ ] 「**切替後 何時間以内なら戻す**」の判断基準を決める。
- [ ] 戻した場合に書き手へ送る**連絡文**を用意。

> 用語: **DNS**＝ドメイン名（30nen.com）と実際のサーバーを結ぶ住所録。**TTL**＝その住所情報が各所にキャッシュされる時間。短くすると変更が速く行き渡る。

## 7. このあとの最初の一歩（Claude Code）

> レビューの助言: **全体の最優先は「Xサーバーへのテストデプロイ＋本番相当ビルド成功」**（§4・クリティカルパス）。
> 下は、それと並行で進める**記事移行トラックの着手手順**。

1. **`wp_id` に unique index を追加**（`articles`、必要なら `users`・`categories`）。先に入れておくと二重取り込みをDB側で防げる。
2. 現行WPから **著者一覧（番号・表示名・メール・記事本数）** を読み取り取得し、`migration/author-map.csv`（仮）のひな形を作る。
3. `reference/categories.json` をもとに、新システムへ連載を作成（`wp_term_id` を紐付け）。
4. 上記が揃ったら **S3 移行スクリプト**の作成に入る（§2 の仕様どおり）。

> 着手は SAKIさんの「進めてOK」を合図にします。
> WordPress本番は読み取りだけ・現行サイトには一切触れません。
