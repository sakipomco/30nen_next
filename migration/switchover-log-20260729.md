## 当日つまずいたこと（手順書に足りなかった3点・次回のために）

### 差異1. 画像のrsyncは「記事投入の前」だけでは足りない

進行表・手順書はステップA（画像rsync）→ ステップE（記事投入）の順だが、これは本移行①向けの順番。
差分移行では **新記事の画像はまだ手元のMacに無く、`migrate-articles --download` で初めて
落ちてくる**ため、ステップAで転送されたのは20ファイル（8.9MB）だけだった。

→ **ステップEのあとに、もう一度 `public/uploads/` を本番へrsyncする**（今回は151MB・689枚）。
　これをしないと、新記事の画像が本番で表示されない。

### 差異2. 🐛 DB差し替え時に「古い作業ファイル（WAL）」を片付けていない

ステップGのとおり `mv` でDBを差し替えたところ、**`database disk image is malformed`
（DBが壊れている）** というエラーになった。

- **送ったファイル自体は無傷**だった（Mac・VPS の md5 が完全一致・Mac側の integrity_check は ok）。
- 原因は、本番の `data/` に **古いDBの作業ファイル `30nen.db-wal` / `30nen.db-shm` が残っていた**こと。
  新しい `30nen.db` を置くと、SQLiteが**古い作業ファイルを新DBのものだと思って重ねてしまい**、
  壊れて見えていた（ファイルは壊れていない）。
- 対処＝`pm2 stop` → 作業ファイルを**対になる古いDBの名前にそろえて退避**
  （`30nen.db.prev-XXXX-wal` / `-shm`。**消さない**＝中身が必要だったため。差異3を参照）
  → `PRAGMA integrity_check` が **ok** → `pm2 restart`。

→ **手順書のステップGを次のように直すべき**（`mv` の直後・再起動の前に）:
```bash
  # 古いDBの作業ファイルを、対になる古いDB名にそろえて退避してから再起動する
  mv data/30nen.db-wal data/30nen.db.prev-<STAMP>-wal 2>/dev/null || true
  mv data/30nen.db-shm data/30nen.db.prev-<STAMP>-shm 2>/dev/null || true
  sqlite3 data/30nen.db "PRAGMA integrity_check;"   # ok を確認してから
  pm2 restart 30nen --update-env
```

### ④ 🐛 robots.txt / sitemap.xml は環境変数を変えただけでは切り替わらない
